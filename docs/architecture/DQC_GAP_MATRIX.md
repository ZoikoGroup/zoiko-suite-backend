### Step K - the first consumer: general-ledger-svc records its reliance (2026-11-26)

| Step | State | What changed |
|---|---|---|
| K - GL journals record reliance | **DONE for the two manual posting routes** | Until now nothing called the reliance API, so every blast radius was empty. **general-ledger-svc** now makes a posted journal a recorded consumer. **Convention:** a journal cites a certification with an evidence reference `certification:<service>:<run_id>` (`service` is `data-quality-svc` or `reconciliation-engine-svc`); any other evidence reference is none of the consumer's business. **Where:** immediately before finalization, after the evidence gate, on `POST /v1/journals/{id}/post` and on `POST /v1/postings/journals` (the approved-journal posting-engine route), each journal recording `general-ledger-svc` / `journal` / its journal id with the issuing service (`internal/certreliance`, wired through `WithCertificationReliance`; URLs `DATA_QUALITY_SERVICE_URL` and `RECONCILIATION_SERVICE_URL`, defaulted and added to the general-ledger-svc compose entry). **It fails closed, like the evidence gate beside it:** a malformed or unknown-service certification reference is **refused (422), never skipped** (a typo must not silently turn a journal that rests on certified evidence into one nobody will be told about); a certification that is **revoked, superseded or past its validity window refuses the posting (422)**, so a journal is not posted on withdrawn evidence; an unknown certification is 422; a principal not permitted to record reliance is 403; a certification service that cannot answer or is not configured is **503 and the journal stays VALIDATED**; a journal that cites a certification when no recorder is wired is 503. A journal that cites no certification is untouched (it never calls the services). One bad certification among several refuses the whole posting. A run id is validated before it reaches a URL (no path or query injection) and a journal cannot supply a service URL. **Ordering and its cost:** recording happens before finalization and is idempotent, so a posting that fails afterwards leaves a reliance for a journal that did not post; that over-names a journal in a blast radius and never under-names it, and a retry records nothing new. Tests: reference parsing (including 11 malformed forms), the client against fake services (request shape and identity headers, every status mapped, unreachable, unconfigured, hand-built references never sent), and handler tests that run **every case against both posting routes**; a mutation check (the gate removed from one route) fails the tests. **Kernel posting path (K2):** the accounting kernel's `POST /v1/accounting-postings` now does the same (the legacy `/v1/postings/events` route takes no evidence references at all and is unchanged). ### Step L - the ledger acts on a withdrawn certification (2026-11-26)

| Step | State | What changed |
|---|---|---|
| L - GL certification watch | **DONE (pull-based; not event-driven)** | Recording reliance told the issuing service what rests on a certification, but a revocation still left the ledger silent. **general-ledger-svc** now closes the loop. **Watch:** every certification a journal or kernel posting relies on is put on a watch list (`certification_watch`, per tenant, legal entity and certification) at the moment its reliance is recorded; if the watch cannot be registered the recording fails and so does the posting, because posting on a certification nobody will ever check again is the silence this ends. **Sweep:** `POST /v1/certification-watch/sweeps {legal_entity_id}` asks each issuing service for the certification's state (its blast-radius read, which both serve; the caller's identity is forwarded) and folds the two vocabularies into one. A run that raises flags logs a **warning**, one with skipped scopes or unchecked certifications logs a warning, and a clean run logs at info; each scope's sweep is bounded to 2 minutes. Tests: config parsing and bounds, the scheduler with fakes (per-scope authorization as the principal with the tenant on the context, isolation of failures, lock behaviour including release on failure, no principal means no run, repeating and stopping), and real Postgres (the scan under row-level security, the read-only capability, the lock under contention, a whole scheduled run raising flags with no one asking, denial skipping a scope, two tenants each swept under its own); **removing the authorization line fails two tests**. offsets are committed after handling, and an event that cannot be handled after three tries is logged and acknowledged (a persistent failure must not block the topic; the sweep is the backstop). `SweepOne` was factored out of the sweep, so a manual sweep, the schedule and an event cannot disagree about what a check is. **Both producers' shapes are read:** data-quality-svc's legacy envelope (`event_type`, `tenant_id`, `payload`; Tests: parsing (both shapes, nothing else, 8 malformed forms), the reactor (per-entity authorization, forged event, unreachable issuer, unwatched certification, re-scan of an already withdrawn one), the consumer loop with a fake broker (acknowledges everything in order, survives read errors, retries then acknowledges, does not acknowledge what a cancelled run did not finish), real Postgres through the real routes, and **a real broker (redpanda, run locally) with a real consumer group reading both topics: both events produced, both journals flagged in about five seconds** (that test runs when `TEST_KAFKA_BROKERS` is set and skips otherwise). **NOT done:** (a) *(closed by L4 for failures and broker errors)*; ## 0. The structural finding

The spec describes one "DQC" plane. The code implements the same ideas in **different services with different vocabularies**,
built to a different document (ZS-SVC-N-001 DATA-02 etc.):

| Spec control | Where it actually lives | Notes |
|---|---|---|
| DQC-01 contract registry | `data-quality-svc` rule sets (+ `schema-registry-svc` for *event* schemas, `data-ingestion-svc` import profiles) | Three unrelated "contract" artifacts; none is a DQC contract. |
| DQC-02 validation / quarantine | `data-ingestion-svc` (quarantine), `data-quality-svc` (Pass/Fail evidence) | DQ never observes data; it records caller-computed outcomes. |
| DQC-03 reconciliation | `reconciliation-engine-svc` | Furthest along. Not deployed in Docker. |
| DQC-04 lineage | `data-lineage-svc` | Entity→activity→entity edges only. |
| DQC-05 certification / exceptions | `reconciliation-engine-svc` (strong) and `data-quality-svc` (weak) | Split. Revocation exists in both (DQ since F3a). |

`com.zoikosuite.accounting.*` (reconciliation). A consumer written to the spec would receive nothing.
