Implementation order — 1 to 102

topological sort of the real dependency graph

Start at step 1 and work down. This is a genuine topological order: no service appears before something it depends on, so you can stop at any step and everything built so far stands up on its own. Within a stage the order is by how much each service unblocks, so the work that removes the most downstream blockage comes first.

Stages are the layers of the graph, not the spec's phases — everything inside one stage is independent of everything else inside it and can be built in parallel by separate people. The needs line under each service is its declared depends_on set with postgres and kafka omitted.

Two things to read carefully. A dotted prerequisite is inferred, not declared: the 20 services that live only in docker-compose.phase5/6/7.yml have no edges into the main graph, so their position comes from the service that owns the data they read. And every service is named by its directory under services/.

Step 1 is not negotiable. authorization-svc unblocks 84 of the other 101 services and they all fail closed. Building anything else first gives you a service that cannot authorize a single write, which presents as a 503 rather than as a missing dependency.

02

What happens to one request

docs/architecture/01-backend.md §04

The canonical execution model for any material action — a payroll release, a contract execution, a payment run. The governance plane sits between every channel and every domain service, and the spec's claim is that it cannot be circumvented by UI flow, internal API, integration, or scheduled automation. Stages 3 and 4 are the gate; everything above them is context assembly and everything below is consequence.

1

Request intake

UI, API, scheduled workflow or system event. Traefik edge does residency steering into a regional pool before anything else sees the request.

gateway :8091 eu-pool / us-pool / uk-pool quarantine-terminator
2

Identity resolution

Resolves authenticated principal, tenant, active legal entity, jurisdictional context, role profile, delegated authority and session trust posture. This is where the envelope in §03 gets populated — downstream services read it and never re-derive it.

identity-context-svc :8080 gateway-auth-svc :8092 tenant-entity-registry-svc :8081 delegated-authority-svc :8136 jurisdiction-rules-svc :8082
3

Governance evaluationthe gate

Policy thresholds, SoD constraints, approval matrices, jurisdictional obligations, documentation requirements and workflow state. POST /v1/authorize unions every active permission bundle on every role the principal holds and answers PERMITTED or DENIED.

authorization-svc :8089 policy-svc :8085 workflow-svc :8090 obligations-svc :8088 evidence-requirements-svc :8130 carta-svc
4

Execution authorizationfail closed

Authorized → the domain service proceeds. Not authorized → denied, escalated, or converted into an approval workflow. Silent failure is prohibited, so a service that cannot reach authorization-svc returns 503 rather than proceeding.

authorization-svc kill-switch-registry-svc :8147 exception-escalation-svc
5

Transaction & event commit

The domain service writes governed state under RLS and emits typed append-only domain events to Kafka. Events are facts, not commands — no consumer may treat one as an instruction.

any of the 80 domain services postgres · one database per service kafka
6

Evidence generation

Captures actor, action, entity, jurisdiction basis, rule set applied, approvals present, referenced documents, timestamps and provenance links. The audit store's hash chain is deliberately global, not per-tenant, so the chain stays verifiable end to end.

audit-event-store-svc :8084 governance-decision-log-svc :8083 workflow-history-svc :8097 evidence-manifest-svc :8095 document-vault-svc :8094
7

Intelligence update

Analytical, forecasting, anomaly and risk services consume the event stream and update derived layers without mutating source truth. Everything here is a projection; none of it is a system of record.

anomaly-detection-svc forecasting-svc compliance-risk-scoring-svc reconciliation-intelligence-svc decision-support-svc :8138 reporting-orchestration-svc

Access model

roles at three different layers

"Role" means three unrelated things in this codebase, and conflating them is the fastest way to a wrong conclusion about who can do what.

1 · Canonical RBAC roles — 12 designed, 0 built

Organization Owner ZoikoSuite Admin Governance / Compliance Admin Finance / Controller Legal / Compliance Reviewer Control Owner Evidence Contributor CIO / Integration Admin AI / Automation Admin Auditor / Read Only Support Agent Zoiko Platform Ops

From the SoD matrix in zoiko_suite_doc7.txt §26. None exists as a constant, enum or seed row — roles are runtime data in authorization_svc.roles, so the count in any tenant is however many an admin creates. Only two role codes have rows today, both test seeds: SERVICECTL_TEST_ADMIN and CONSOLE_DEMO_OPERATOR. The first holds every HR action across four services at once, which its own seed file calls "the opposite of segregation of duties".

The other ~60 services still connect as the shared zoiko_app — their tenant isolation rests only on the explicit tenant_id = $n predicate in each store, with the policy inert behind it.

Standing the stack up

the order, condensed

Sequence

  1. Infrastructure — postgres, kafka, redis, minio, opensearch, otel-collector.
  2. init-db.sh — one database per service, then run every service's migrations as the owner.
  3. create-app-roles.sh — after migrations. It grants on tables that exist now and sets ALTER DEFAULT PRIVILEGES so later migrations stay reachable. Run it before and a service sees a missing-grant failure that looks like a missing row.
  4. Steps 1–102 in order, per §01. authorization-svc first, always.
  5. seed-rbac.sql, then seed-rbac-hr.sql — the second reuses the first's role, tenant and principal, so order matters. Both need app.tenant_id set first or RLS refuses the insert.
  6. gateway last — it depends on the regional pools and gateway-auth-svc.

Traps worth knowing

  1. A superuser bypasses RLS unconditionally, FORCE included. An isolation test over the postgres connection proves only the application predicate — it never touches the policy. Use a purpose-created ordinary role.
  2. Always run a negative control. Remove the migration; the test must fail. An over-restrictive policy is a real failure mode too — one hid every global config default and turned applicable config into "not found".
  3. Three services need a deliberate cross-tenant exemption — audit-event-store-svc (global hash chain), authorization-svc (FindGrantedActions), secret-vault-integration-svc (admin rotate). Check for a legitimate cross-tenant caller before writing the policy, not after.
  4. Test harnesses that name migrations individually silently skip new ones. Confirm the suite globs *.up.sql before trusting a green run.
  5. Verification loop per service: gofmt -w . → go build ./... → go vet ./... → go test ./... -count=1.
