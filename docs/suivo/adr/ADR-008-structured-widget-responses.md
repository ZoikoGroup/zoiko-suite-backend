# ADR-008: Structured widget responses (menu, follow-ups, CTA, outcome)

- Status: Proposed — pending Backend Lead + Product
- Date: 2026-10-30
- Context: The widget's guided menu and follow-up questions were hard-coded in the browser. Doc 02 §08 forbids new categories and headings that are not in the canonical intent catalog, and the follow-ups have to come from approved content, never the model. Sources showed "Approved ZoikoSuite source" when a claim cited a route key (for example `pricing`) that is not a KB source. See `docs/suivo/gap-analysis-structured-widget.md`.
- Decision: Additive, optional contract fields behind the `structured_response_enabled` flag (default **off**), so existing clients see the unchanged R0 contract.
  - `GET /public-ai/v1/menu` → `{schema_version, categories[{id, label, items[{id, label, intent_id, message}]}]}`. Categories are the Doc 02 §22 public page families, labelled with the Homepage chips (Explore platform, Compare plans, Security & trust, Book demo) plus Support Center; items are each family's recommended chips, mapped to their Doc 02 §06 intent. Defined in `internal/policy/menu.go`. A test checks every item's message classifies to its intent, so a click goes through the same policy as typed text. 404 while the flag is off.
  - Turn `followups[]` (max 4) after ANSWERED or HANDOFF: the Doc 02 §08 secondary-intent pairs first, then the other items of the same family, in menu order. Deterministic; the model never selects them. Refusals and abstentions keep their existing `suggestions[]`; CLARIFY keeps its options.
  - Turn `cta`: at most one `primary` and one `secondary` `{route_key, label, url?}` built from `actions[]`. The primary label is the intent's Doc 02 §06 "Default CTA". `url` is set only when the signed route registry has a real page (placeholders are never sent).
  - `citations[]` gain `title`, `route_key` and `url`, resolved server-side: KB sources from the release's source registry; route-keyed claim citations from `policy.RouteTitles` and the route registry.
  - Turn `outcome`: GROUNDED (ANSWERED), CLARIFY, ABSTAIN, SAFE_FALLBACK (UNAVAILABLE), REFUSED (REFUSED_ACTION), HANDOFF_OFFER (HANDOFF). CLARIFY is added to the five outcomes in the gap analysis because a clarifying question neither answers nor abstains.
  - Local dev: `PUBLIC_AI_STRUCTURED_RESPONSE=true` sets the flag at start for the in-memory or seeded dataset (dev/test only; config refuses it elsewhere). It goes through `flags.Set` with actor and approval references like any other change.
- Not in this decision: `blocks[]` (server-assembled answer blocks), `/config` trust claims and static fallback fields (gap analysis items 2 and 4–5 of section 1, item 8). They need their own design and approval.
- Consequences: The widget can drop its hard-coded topic list. The menu changes only with the policy version. Once the signed Services/Categories Reconciliation v2.1 exists (Doc 02 §08 checkpoint), the menu and follow-up map should be re-derived from it.
